## 현재 SAFE인데 최종 DANGER였던 원인과 해결

기존 서버 `risk.py`가 `hazard_latched`이면 현재 SITE와 관계없이 `risk=DANGER`를 반환했다.
프런트 `riskPresentation()`도 같은 조건으로 표시를 다시 DANGER로 강제했다.
수정 전 실제 API에서 `site_state=SAFE`, `risk=DANGER`, `hazard_latched=true`, `reset_allowed=true`를 확인했다.
카메라별 단독 판정이 아니라 사람별 결합 판정을 최종 상태로 사용하는 요청과 맞지 않았던 부분이다.

이제 API의 `risk`와 `site_state`는 현재 결합 판정으로 일치한다. 이전 위험 이력은 별도의 황색 표시로 남긴다.
현재 SAFE라면 `restriction_required=false`이며 이력만으로 제한 필요를 표시하지 않는다.
변경 후 15초 동안 30회 API를 조회했고, 30회 모두 이력이 있는 상태에서 현재 SAFE와 최종 SAFE가 일치했다.

## RESET이 보이지 않거나 안 눌리는 문제

기존 `.reset-row`의 `margin-top:auto`가 왼쪽 작업자 표 높이에 맞춰 늘어난 오른쪽 카드 맨 아래로 버튼을 밀었다.
활성 버튼 색도 비활성 버튼과 같았고, 현재 SAFE 조건이 잠깐 바뀌면 버튼 자체가 비활성화됐다.
브라우저 확인 팝업을 호출하는 방식에도 의존하고 있었다.

버튼을 상태 설명 아래로 배치하고 활성 색을 파란색으로 구분했다. 메인과 관리자 화면에 같은 RESET 기능을 제공한다.
위험 이력이 있고 연결이 정상이면 버튼을 누를 수 있으며, 조건 미충족 시 이유를 표시한다.
화면 안의 '작업자 이탈을 직접 확인했습니다' 확인란을 체크한 뒤 누른다.
서버는 현재 사람별 결합 SAFE·현재 episode ID·기록 상태를 다시 검사한 뒤 이력만 해제한다.
위험 이력이 없거나 연결이 없으면 비활성화하며 이유를 표시한다. 위험 중 RESET으로 현재 판정을 SAFE로 바꾸지는 않는다.

## FPS 원인과 해결

기존 `priority_weight=3`이 CAM1의 단독 DANGER에 추론을 몰아줬다. 현재 결합 SAFE여도 우선 배정이 계속됐다.
수정 전 최근 1,000프레임의 배정은 CAM1 712회, CAM2 288회였다.

기본 가중치를 1로 바꿔 양쪽 준비된 카메라에 추론을 균등 배정한다. 모델은 기존 단일 GPU 작업자를 유지한다.
한 프레임에서 위험 결합을 두 번 계산하던 부분을 한 번으로 줄였다.
ID를 붙이기 전에 만들고 곧바로 다시 만들던 Ground/Risk JSON을 제거했다.
0.1초 건강 확인 때 전체 API 스냅샷을 복사하던 작업과, 프레임·스케줄러의 보정 확인 때 전체 보정 정보를 복사하던 작업도 줄였다.
영상 갱신 상한은 10→15FPS로 올렸다. 이는 추론 FPS와 별개다.

| 항목 | 수정 전 | 수정 후 |
|---|---:|---:|
| CAM1 추론 FPS | 16.53 | 12.82 |
| CAM2 추론 FPS | 7.04 | 12.89 |
| 전체 추론 FPS | 23.57 | 25.71 |
| SITE 처리 평균, 최근 500프레임 | 1.66ms | 1.10ms |

실행 중인 API의 완료 프레임 카운터 증가량으로 측정했다. 수정 전은 약 6초, 수정 후는 약 15초 표본이며 장기 부하 시험은 아니다.
전체 FPS 개선은 약 9.1%, CAM2는 약 83.2%다.
CAM1의 감소는 두 카메라에 추론 기회를 나눈 결과다.
모델 자체 GPU 추론은 여전히 평균 약 21.9ms, YOLO 후처리는 약 7.7ms를 사용한다.
같은 모델에서 각 카메라 30FPS를 보장하는 변경은 아니다. 현재 CAM2 캡처 입력은 실측 15FPS다.
